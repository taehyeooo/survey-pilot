# 0014 spec 요구사항 ID를 plan과 테스트가 인용한다

## 결정
- spec 요구사항 항목 맨 앞에 굵은 `R-<번호>`(spec마다 1부터)를 붙인다: `- **R-1** ...`.
- plan은 체크 단계 줄 끝에 `(R-1, R-3)`처럼 인용한다.
- 테스트는 `<slug>#R-<번호>`로 요구사항을 인용한다. slug는 spec 파일 이름에서 앞 날짜와 `.md`를 뺀 것이다. 주석이든 테스트 이름이든 언어 습관대로 쓴다.
- `scripts/check_docs.py`([0009](0009-docs-check-ci.md))가 검사한다.
  - **실패**: 한 spec 안 ID 중복, ID가 active plan의 체크 단계 어디에도 없음, plan·테스트가 없는 ID를 인용함.
  - **경고**: ID 있는 spec에 plan이 아직 없음, 테스트가 인용하지 않은 요구사항(연결률을 출력).
- 옵트인: ID가 없는 spec은 이 검사를 받지 않는다.
- 지운 번호는 다시 쓰지 않는다. 뜻이 바뀌면 새 번호를 쓴다.
- 연결률은 "테스트가 있다"이지 "구현이 맞다"가 아니다. 구현이 맞는지는 코드를 읽는 사람 리뷰가 판단한다.

## 이유
- 버전 검사([0004](0004-doc-versioning-frontmatter.md))만으로는 요구사항이 늘어도 `based_on`만 올리면 통과한다. 빠진 구현 단계가 PR에서 잡혀야 한다.
- 기계가 확실히 판단할 수 있는 부분(ID가 있나, 인용했나)만 CI로 두면 결과가 흔들리지 않고 비용이 들지 않는다([0002](0002-cost-zero-free-tiers.md)).
- plan이 없는 spec을 실패시키면 "spec 먼저 쓰고 결정받은 뒤 plan" 흐름을 막는다. 그래서 경고만 한다.
- 연결률을 실패 기준으로 두면 숫자를 채우려는 억지 인용이 생긴다.

## 비교한 대안
1. 모든 spec에 강제 — 기존 문서를 한꺼번에 고쳐야 한다. 옵트인으로 시작한다.
2. AI 명령으로 일치 여부만 보고 — 돌리는 것을 잊고, 결과가 실행마다 다르다.
3. plan 단계에도 ID를 붙여 양방향 검사 — 정리 단계처럼 요구사항이 없는 단계가 있어 맞지 않는다.

## 확인 방법
- `scripts/check_docs.py`와 그 테스트(PR CI에서 실행). 구현 판단은 사람 리뷰.

## 다시 볼 조건
- ID를 붙인 spec이 대부분이 되면 새 spec에는 강제하는 것을 검토한다.
- 연결률이 여러 PR에서 안정되면 기준값(예: 80% 미만 실패)을 정한다.
