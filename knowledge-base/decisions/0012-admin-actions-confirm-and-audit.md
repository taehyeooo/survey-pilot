# 0012 관리자·운영 조치는 미리보기 → 사유·재확인 → 실행, 그리고 감사 기록

## 결정
사용자 데이터나 서비스 상태를 바꾸는 관리자·운영 조치(계정 정지·삭제, 점검 모드 같은 운영 스위치, 환불 같은 돈이 움직이는 조치)는 아래 틀로만 한다.

1. **미리보기** — 무엇이 어떻게 바뀌는지 보여 주고 확인 토큰을 준다. 미리보기는 아무것도 바꾸지 않는다.
2. **사유·재확인** — 사유를 받는다. 되돌리기 어려운 조치는 확인 글자를 다시 입력하게 한다.
3. **실행** — 확인 토큰(짧은 유효 시간, 한 번만, 그 관리자·조치·대상·값에 묶임)이 맞을 때만 실행한다. 실행할 때 미리보기의 검사를 다시 한다.
4. **감사 기록** — 실행마다 누가·무엇을·누구에게·왜·결과를 남긴다. 바깥 작업이 실패해도 시도 기록은 남기고, 수정·삭제 경로를 두지 않으며, 개인정보 대신 내부 번호만 적는다.
5. **새 조치는 이 틀에 꽂는다.** 틀을 거치지 않고 데이터를 바꾸는 관리자 API를 따로 만들지 않는다. 관리자 확인은 경로 단위로 자동으로 걸고, 전수 권한 테스트로 한 번 더 지킨다.

## 이유
- 관리자 실수(다른 대상 클릭, 두 번 누르기)는 한 번이면 되돌리기 어렵다. 미리보기와 확인 글자가 그 한 번을 막는다.
- 조치마다 확인을 직접 부르게 하면 언젠가 한 곳에서 빠진다. 경로 단위 자동 적용과 전수 테스트가 이중 안전장치다.
- 감사 기록이 없으면 "누가 왜 이렇게 했나"를 사람에게 물어야 한다. 고칠 수 있는 기록은 기록이 아니다.
- AI 에이전트가 운영 조치를 할 때도 같은 경계(상태를 바꾸면 사람 확인)를 쓸 수 있다.

## 비교한 대안
1. 확인 대화상자("정말요?")만 — 습관적으로 누르게 되고, 서버는 확인했는지 모른다.
2. 감사 기록을 애플리케이션 로그로 — 로그는 돌고 지워지며 대상별 이력을 찾기 어렵다.
3. 조치마다 API를 따로 — 확인·기록을 빠뜨리는 곳이 생긴다.

## 확인 방법
- 사람 리뷰: 관리자 기능 PR에서 이 틀을 거치는지 본다. 구현이 있으면 토큰 재사용·다른 대상·사유 누락이 거부되는지, 전 관리자 API 권한을 훑는 테스트로 지킨다.

## 다시 볼 조건
- 관리자가 여러 명이 되어 권한을 나눠야 하면 역할 체계를 검토한다.
- 금액이 큰 조치가 생기면 두 사람 확인·금액 한도가 필요한지 본다.
