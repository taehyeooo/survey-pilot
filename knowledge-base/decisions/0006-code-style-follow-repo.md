# 0006 코드 스타일은 레포가 실제로 쓰는 방식

## 결정
- 새 코드는 그 레포(또는 하위 프로젝트)가 실제로 쓰는 방식을 따른다. "일반적인 표준 스타일"로 바꾸지 않는다.
- 스타일 규칙을 정할 때는 기존 코드를 집계해서 근거로 남긴다(예: 들여쓰기 종류, 특정 문법 사용 횟수).
- 다른 스타일로 일괄 포맷을 바꾸는 것은 열린 브랜치가 머지된 뒤, 포매터 도입과 함께 별도 PR 하나로만 한다.
- 고치려는 파일의 기존 스타일 문제는 그 파일을 고칠 때만 함께 정리한다.
- 하위 프로젝트별 상세 스타일은 그 폴더의 README나 CLAUDE.md에 둔다.

## 이유
- 한 파일 안에 스타일이 섞이면 읽기 어렵고, 리뷰에서 스타일 논쟁이 생긴다.
- AI는 "흔한 스타일"로 쓰려는 경향이 있어, 기준이 없으면 레포마다 스타일이 흔들린다.
- 기능 변경과 일괄 포맷이 한 PR에 섞이면 무엇이 바뀌었는지 리뷰할 수 없고, 열린 브랜치들과 충돌한다.
- 집계 근거가 있으면 "원래 이렇게 썼다"를 두고 다투지 않는다.

## 비교한 대안
1. 처음부터 표준 스타일로 통일 — 기존 코드 전체를 바꿔야 하고 열린 작업과 충돌한다.
2. 스타일을 정하지 않고 각자 쓰기 — 파일마다 달라지고 AI도 기준을 잡지 못한다.

## 확인 방법
- 사람 리뷰: PR diff에 기능과 관계없는 대량 포맷 변경이 섞였는지 본다. 포매터를 들이면 그 포매터의 CI 검사로 바꾼다.

## 다시 볼 조건
- 포매터·린터를 CI에 넣으면 이 ADR의 확인 방법을 그 검사로 바꾼다.
- 하위 프로젝트끼리 스타일 차이가 협업을 방해하면 통일 PR을 검토한다.
